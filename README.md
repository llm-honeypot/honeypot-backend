# VaultBank Honeypot — Backend

A production-quality fake Indian banking server that traps attackers, classifies their techniques, and generates convincing fake responses — all while logging everything to DynamoDB and streaming live telemetry to a SOC dashboard.

```
Attacker hits any endpoint
        │
        ▼
  classifier.py  ──▶  identifies attack type + scores the request
        │               (SQL injection, brute force, path traversal, RCE, etc.)
        ▼
  session_manager.py  ──▶  gets/creates attacker session in DynamoDB
        │                    tracks cumulative score → escalates stage 0→1→2→3
        ▼
  deception.py  ──▶  generates a convincing fake response
        │             stage 0: generic 404
        │             stage 2+: full fake data or LLM-generated response
        ▼
  WebSocket broadcast  ──▶  pushes live event to SOC dashboard
```

---

## How It Works

### 1. Attack Classification (`classifier.py`)

Every incoming request is scored against pattern libraries:

| Attack Type | Example Signal | Score |
|---|---|---|
| SQL Injection | `?id=1 UNION SELECT` in query string | 25 |
| Path Traversal | `/../../../etc/passwd` in path | 20 |
| Credential Harvest | `GET /.env`, `GET /config.json` | 15 |
| Brute Force | Repeated `POST /api/auth/login` | 8/req |
| RCE | `POST /api/execute` with shell commands | 30 |
| SSRF | Requests to `169.254.169.254` (AWS metadata) | 20 |
| Dir Enum | Scanning `/admin`, `/backup`, `/phpinfo.php` | 5 |

### 2. Stage Escalation (`session_manager.py`)

The honeypot gets **more generous** as attackers probe more — wasting their time and making the trap more convincing:

| Stage | Score Threshold | What the attacker gets |
|---|---|---|
| 0 | < 10 | Generic 404 / denial |
| 1 | 10–29 | Partial data (masked fields) |
| 2 | 30–59 | Full fake records, `.env` with credentials |
| 3 | 60+ | SQL dump, fake JWT tokens, canary tokens |

Sessions are persisted in DynamoDB so stage survives restarts and scales across instances.

### 3. Deception Engine (`deception.py`)

At stage 2+, responses are generated by **Groq (LLaMA 3.1)** with banking-specific prompts:

- **SQL Injection** → LLM returns a JSON array of 8 fake Indian bank customers (name, PAN, Aadhaar last-4, balance, IFSC)
- **Credential Harvest** → LLM generates a realistic `.env` with fake `CORE_BANKING_DB_URL`, `JWT_SECRET`, AWS keys
- **Path Traversal** → LLM returns a fake `/etc/passwd` with banking Linux users (`vaultbank`, `postgres`, `vb-fraud-ai`)
- **RCE** → LLM returns realistic terminal output for the attacker's command, run as `www-data` on `prod-vaultbank-core-01`
- **SSRF** → Static fake AWS metadata endpoint response (always)

Each attacker gets **unique** fake data — different names, different balances — making it harder to fingerprint as a honeypot.

### 4. Bait Endpoints

| Method | Path | Bait Type |
|---|---|---|
| `GET` | `/` | VaultBank login page (HTML) |
| `POST` | `/api/auth/login` | Brute force bait |
| `GET` | `/api/customers?id=` | SQL injection bait |
| `GET` | `/api/accounts` | Data exfiltration bait |
| `GET` | `/api/transactions` | Data exfiltration bait |
| `GET` | `/.env` | Credential harvest bait |
| `GET` | `/config.json` | Credential harvest bait |
| `GET` | `/backup/db.sql` | SQL dump bait |
| `GET` | `/etc/passwd` | Path traversal bait |
| `GET` | `/admin/debug` | Recon bait (fake sysinfo JSON) |
| `GET` | `/internal/services` | Recon bait (fake microservices map) |
| `POST` | `/api/execute` | RCE bait |
| `WS` | `/ws` | Live telemetry to SOC dashboard |

### 5. Live SOC Feed (`/ws`)

Every event is broadcast over WebSocket to connected SOC dashboards:

```json
{ "type": "event",          "payload": { "attack_type": "sql_injection", "threat_level": "hostile", "ip": "...", "payload": "1 UNION SELECT..." } }
{ "type": "profile_update", "payload": { "session_id": "...", "stage": 2, "total_score": 55.0, "tags": ["#sqli", "#cred-hunt"] } }
{ "type": "stats",          "payload": { "active_sessions": 3, "attacks_intercepted": 47, "total_time_wasted": 1820 } }
```

## Stack

- **FastAPI** + **uvicorn** — async Python web server
- **Groq (LLaMA 3.1 8B)** — LLM for dynamic fake response generation
- **DynamoDB** — persistent session and event storage (ap-south-1)
- **WebSocket** — live push to SOC dashboard
- **Python 3.11** on Amazon Linux 2023 (EC2 t2.micro)

---

## Deployment

### Environment (`.env`)

```env
APP_ENV=production
USE_LLM=true
USE_DYNAMODB=true
GROQ_API_KEY=your_groq_key
LLM_MODEL=llama-3.1-8b-instant
DYNAMODB_SESSIONS_TABLE=honeypot-sessions
DYNAMODB_EVENTS_TABLE=honeypot-events
DYNAMODB_REGION=ap-south-1
JWT_SIGNING_KEY=32_random_hex_chars
```

### Run locally

```bash
pip install -r requirements.txt
cp .env.example .env  # fill in values
uvicorn main:app --host 0.0.0.0 --port 8000
```

### EC2 (systemd)

```bash
# Service runs as: /usr/bin/python3.11 -m uvicorn main:app --host 0.0.0.0 --port 8000
systemctl status honeypot.service
journalctl -u honeypot.service -f
```

nginx proxies port 80 → 8000 and handles `/ws` WebSocket upgrade.

## DynamoDB Schema

**`honeypot-sessions`** — one item per attacker IP
```
session_id (PK)  ip  stage  total_score  attack_types_seen  tags  request_count  first_seen  last_seen
```

**`honeypot-events`** — one item per request
```
id (PK)  session_id  timestamp  attack_type  threat_level  method  path  payload  response_type  score
```

## Fake Data (`fake_data.py`)

All data is entirely fabricated. Nothing here is real:

- 8 fake Indian bank customers (names, PAN, Aadhaar last-4, account numbers, balances)
- 3 fake bank employees with branch codes
- Fake `.env` with plausible-looking but non-functional credentials
- Fake PostgreSQL dump of `customers` and `accounts` tables
- Fake `/etc/passwd` with banking Linux users
- Fake `config.json` with internal `.internal` hostnames
- Fake AWS metadata endpoint response
